# Friends Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** People can send, accept, decline, cancel and remove friend requests, block others, and see a friend's shared summary next to their own; the Friends visibility becomes real.

**Architecture:** A pure `public/friends.js` (pair ids, the exact write plans, grouping, relation, comparison) is unit-tested. The security rules are the core: `friendships/{pairId}` and `blocks/{blocker}_{blocked}`, plus a changed `profiles` read rule, validated by emulator tests in `tests-rules/`. `index.html` gets live listeners, a Friends screen with a friend page, and the Find-a-friend box moves there.

**Tech Stack:** plain JS ES modules, `node --test`, Firestore rules, Firebase emulator (`tests-rules/`, Java 21 on PATH: `/c/Program Files/Eclipse Adoptium/jdk-21.0.12.101-hotspot/bin`), headless Edge + Firebase-stub harness (`$TEMP/harness`, port 5071) for screenshots.

**Spec:** `docs/superpowers/specs/2026-10-19-friends-design.md` (binding; it holds the data model and rules, which this plan does not repeat).

## Global Constraints

- No new dependency, no build step; root `npm test` runs only `tests/`, `tests-rules/` stays separate.
- `index.html`, `lang-ar.js`, `sw.js` have CRLF endings: edit with Edit or Write-tool scripts (`$TEMP/ed.cjs`-style), never heredoc regexes with backslashes/apostrophes.
- Existing rules (`users/{uid}/items`, `usernames`, `emails`, profile write rules) keep their meaning. Only the profile **get** rule gains the friends clause.
- Pair id = the two uids sorted ascending joined by `_`. Status values exactly `pending` / `accepted`. Write plans have the shape of `planShare`: `{op:"set"|"update"|"delete", path:[...], data?}`.
- A write plan never touches a document that may not exist unless the rule allows it: deletes of missing `friendships`/`blocks` docs are allowed by the rules (`resource == null ||`).
- Every new user-visible string goes through `t()`/`tn()` with an Arabic entry in `public/lang-ar.js`; usernames are never translated.
- Client caps: 100 friends, 30 pending sent. Writes need a connection (offline → existing offline toast).
- Bump `iron-log-v18` and add `/friends.js` to `APP_SHELL` in the release task only. Nothing is deployed before the final review and the user's go-ahead.

## Review Focus

- A stranger reading/listing others' friendships or blocks, forging a request for someone else, with a fake name, or over a block → Task 2 named emulator tests.
- Anyone but the non-requester accepting; accepted→pending downgrade; changing `users`/`requester`/the other's name → Task 2 tests.
- Friends-only profile read: works for accepted pairs only, stops right after remove or block, never for pending → Task 2 tests (read before/after each state).
- Block must remove the friendship and stop re-requests; the blocked person cannot read the blocker's blocks → Task 1 `planBlock` test + Task 2 tests.
- Hidden/private person revealing more than `@username` exists; email search not changed → Task 3 `lookupResult` tests.
- Both people requesting at once ends as one pair doc, the UI offering "Accept" → Task 2 test (second create denied) + Task 1 `relationTo` test.

### Task 1: `public/friends.js` — pure friend logic

**Files:**
- Create: `public/friends.js`, `tests/friends.test.js`

**Interfaces:**
- Produces (all exported; no DOM, no Firebase):
  - `pairId(a, b) → string` (`"min_max"`; throws on equal or empty)
  - `planRequest({me, meName, other, otherName, now}) → {ops}`: one `set friendships/<pair>` with `{users:[sorted], requester:me, status:"pending", names:{[me]:meName,[other]:otherName}, updated:now}`
  - `planAccept({me, other, now}) → {ops}`: `update friendships/<pair>` `{status:"accepted", updated:now}`
  - `planRemove({me, other}) → {ops}`: `delete friendships/<pair>` (decline, cancel, remove friend)
  - `planBlock({me, other, now}) → {ops}`: `set blocks/<me_other>` `{blocker:me, blocked:other, updated:now}` then `delete friendships/<pair>`
  - `planUnblock({me, other}) → {ops}`: `delete blocks/<me_other>`
  - `planNameRefresh({me, other, myName, now}) → {ops}`: `update friendships/<pair>` `{["names."+me]: myName, updated: now}`
  - `groupFriendships(docs, me, blocks) → {requests, friends, sent, blocked}`: `docs` = friendship data objects, `blocks` = block data objects; each item `{uid, name, updated}` (`uid`/`name` = the OTHER person; `blocked` items come from `blocks.blocked`, name from any friendship `names` else `null`); `friends` sorted by name (case-insensitive), the rest newest first
  - `relationTo(me, other, docs, blocks) → "self"|"blocked"|"friends"|"sent"|"received"|"none"` (`blocked` = I blocked them)
  - `compareSummaries(mine, theirs) → [{key, mine, theirs, leader:"me"|"them"|"tie"}]` over keys `level, workoutsWeek, workouts30, streakWeeks, volumeWeekKg, prs30, workoutsTotal` in that order; a missing summary counts as 0 for every key
- Consumes: nothing.

- [ ] **Step 1: Write the failing tests** in `tests/friends.test.js` (Node test runner, same style as `tests/social.test.js`):
  - `pairId("b","a") === pairId("a","b") === "a_b"`; throws for equal ids.
  - `planRequest` data exactly as above (uids `"u2"`,`"u1"` give `users:["u1","u2"]`); `planAccept`/`planRemove`/`planUnblock`/`planNameRefresh` paths and data; `planBlock` ops are `["set blocks/u1_u2","delete friendships/u1_u2"]` in that order.
  - `groupFriendships`: pending created by me → `sent`; pending created by them → `requests`; accepted → `friends` (sorted "Ann" before "bob"); a block → `blocked`; docs of other pairs not involving `me` are ignored.
  - `relationTo` for all six results, including: a block wins over a friendship; both-sides-asked is impossible in data so a pending doc created by them is `received`.
  - `compareSummaries`: higher level → `"me"`; equal → `"tie"`; `theirs = null` → every `theirs` 0 and leaders `"me"` where mine > 0; order of keys as listed.

- [ ] **Step 3: Implement** the functions in `public/friends.js` as specified above.
- [ ] **Step 4: Run** `npm test` — Expected: all pass (202 + new).

### Task 2: Security rules and emulator tests

**Files:**
- Modify: `firestore.rules`, `tests-rules/firestore.rules.test.js`

**Interfaces:**
- Consumes: Task 1 doc shapes (spec "Data" section is the contract).
- Produces: rules for `friendships/{pairId}` and `blocks/{blockId}`; `profiles` get rule extended.

- [ ] **Step 1: Write the failing tests** (append to `tests-rules/firestore.rules.test.js`; add a helper `pair(a,b)`, seed helpers for claims of `u1`,`u2`,`u3` named `ziad`,`zed`,`omar`, and a `friendDoc(requester, status)` builder). One named test per line:
  - friendships: stranger `u3` cannot get or list a `u1_u2` pair; `u1` can get it and can query `where("users","array-contains","u1")`; a query without the `array-contains` filter is denied.
  - create: `u1` requests `u2` with valid names → allowed; denied when: `requester` is the other person, status `accepted`, `users` not sorted, id not matching `users`, my name entry ≠ my profile username, the other's name entry not pointing at that uid in `usernames`, extra keys, I have no profile/username, `u2` has blocked `u1` (`blocks/u2_u1` exists).
  - duplicate: with a pending `u1→u2` doc, `u2` creating the same pair (overwriting with themselves as requester) is denied.
  - accept: `u2` (non-requester) may set `pending→accepted` changing only `status` and `updated`; the requester `u1` may not accept; changing `users`, `requester` or `names` in the same write is denied; `accepted→pending` is denied for both.
  - name refresh: `u1` may change only `names.u1` to their current profile username (status unchanged); changing `names.u2` is denied.
  - delete: either person may delete; a stranger may not; deleting a missing doc is allowed for a person who would be in it? (rule is `resource == null || uid in users`: assert a signed-in user deleting a non-existent pair succeeds).
  - blocks: `u1` creates `blocks/u1_u2` (`blocker:"u1"`, `blocked:"u2"`); `u2` creating `blocks/u1_u2` is denied; id not matching `blocker_blocked` is denied; only the blocker can get/delete it; `u2` cannot get it; list is denied except with `where("blocker","==",me)` (query as `u1` succeeds, as `u2` for u1's is denied).
  - block batch: `u1` batch (set block + delete accepted pair) succeeds, then `u2` cannot re-request.
  - profiles get: with `u2` profile `friends`: `u1` denied while no pair, denied while `pending`, allowed when `accepted`, denied again after the pair is deleted; with `private`: denied even when `accepted`; with `public`: allowed for anyone signed in; the owner always.
- [ ] **Step 2: Run** `cd tests-rules && npm test` (Java 21 on PATH) — Expected: the new tests FAIL, the 23 existing pass.
- [ ] **Step 3: Implement the rules** in `firestore.rules`: helper `pairPath(a,b)` = `/databases/$(database)/documents/friendships/$(a < b ? a + '_' + b : b + '_' + a)`, `areFriends(uid)` (pair exists and `status == 'accepted'`), then the `friendships` and `blocks` matches exactly per the spec's Rules section (`get` allowed when `auth.uid in resource.data.users`; `list` same condition so only `array-contains` queries pass; delete = `resource == null || auth.uid in resource.data.users`; blocks delete = `resource == null || resource.data.blocker == auth.uid`), and extend `profiles` get with `|| (resource.data.visibility == 'friends' && areFriends(uid))`.
